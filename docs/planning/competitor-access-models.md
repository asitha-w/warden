# How other operations agents reach customer infrastructure, 2026-10-31

Twenty products, vendor documentation only. Five research reports in `research/` hold the detail and every source URL; this file is the comparison and what it means for Warden. Where a vendor's docs say nothing, the table says "not published". Marketing claims that the docs do not back are called out as such.

## What the field agrees on

1. **Read-only is the default everywhere**, and actions are a separate, explicit grant: a second role (AWS elevated role, Azure Privileged level, Sedai Autopilot), a second credential, or a per-action enable (Resolve, Datadog Guardrails).
2. **The in-cluster component is outbound-only on 443**, authenticated by a one-time enrollment token or a keypair the vendor never holds, runs non-root with capabilities dropped, ships as a signed image with an SBOM, and carries a read-only ClusterRole: get, list, watch, no Secrets, no exec. Komodor and Parity are the exceptions, and both have moved governance to a policy layer outside the agent to compensate.
3. **Nobody reaches into a VM.** The hyperscalers' own agents document no in-guest path. Only PagerDuty (through Rundeck's SSH, WinRM and SSM) and Shoreline (a host agent with sudo) execute on hosts, and Datadog's runner executes only scripts declared ahead of time in a config file. Every AI-native startup is Kubernetes and cloud API only.
4. **The model never holds a write credential.** Resolve's execution engine, Komodor's MCP gateway, AWS's session-policy ceiling, Azure's tool policies and Komodor's five external gates all put the decision and the credential outside the reasoning loop.
5. **Approvals bind to the exact call.** Komodor grants are single-use and specific to the tool call and its arguments; AWS approvals are single-use or reusable for four hours; Resolve proposals expire.
6. **Cloud identity is federated where the vendor can manage it.** AWS: cross-account role with external ID, or OIDC federation. Azure: most vendors still use an app registration with a client secret; Traversal is the one that runs its own OIDC issuer and asks the customer for a secretless federated credential, with a Bicep template.
7. **Egress IPs are a published contract** for the vendors that reach public endpoints: a CIDR, a machine-readable list, notice before changes. Cleric assigns a static IP per customer instance.
8. **Validation at connect time**: Cleric inspects the IAM role at save time and refuses one that carries write permissions; Azure SRE Agent derives roles from the resource types it finds.
9. **Data leaves only after redaction**, with zero-retention agreements at the model providers and no training on customer data, stated plainly on a security page.

## What this means for Warden

Warden is choosing to do the one thing the field avoids: act inside VMs. That is the gap, and it carries the burden the others declined. The published patterns tell us how to carry it.

1. **Hands on a VM are a catalogue, not a shell.** Datadog's runner executes only predefined scripts, PagerDuty's SSM action offers three operations and no free text. Warden's `run_command` becomes a catalogue of declared actions per cell kind (restart a unit, rotate a log, clear a path, read a named file), each with parameters, preconditions and a verification. A free-form command exists only under an `ask` policy and shows the exact command in the approval.
2. **The approval binds to the exact arguments**, is single-use, expires, and is answered only in the console. Warden's approval already carries the command; add expiry and argument binding.
3. **Azure identity: offer federation, not only a client secret.** Traversal's pattern is exactly the bring-your-own-app flow in RESUME.md: Warden runs an OIDC issuer, the customer's app registration trusts it, no secret is stored. Ship a Bicep template with the role assignments.
4. **Validation refuses what it did not ask for.** When a connection is validated, list the role assignments and refuse to mark it connected if the read identity carries write actions, as Cleric does. The capability list on the connection page comes from this.
5. **The probe follows the in-cluster norms list**: outbound only, enrollment token, signed image, non-root, read-only ClusterRole with no Secrets and no exec, namespace scoping, a destination allowlist on anything that proxies. Since Warden's cluster probe is an unmodified collector, this is mostly a packaging and documentation obligation.
6. **Publish the tenant's egress IP as a contract**: on the tenant page, in the API, with notice before it changes. Cleric's per-instance static IP is the closest analogue to Warden's per-tenant static egress.
7. **The read-only ceiling is enforced below the policy gate.** AWS's session policy is the model: even if a responder's policy says allow, the identity used for investigation cannot write. Warden's read and write scopes on a connection already separate the identities; the toolbox must use the read identity for every read tool, and the remediator alone holds the write one.
8. **Document the security page early.** Every credible vendor has one page that states: what is installed, what it can and cannot do, egress endpoints, how credentials are held, redaction, model providers, retention. Warden needs the same page before the first external user, and the planning files here are its draft.

## Where Warden differs on purpose

- The target customer runs VMs on Azure and UpCloud without an SRE. The field's Kubernetes-only reach leaves them out, and that is Warden's reason to exist.
- Warden's probe is a telemetry collector the customer may already run; the others ship a proprietary satellite or nothing.
- Warden owns the whole loop from signal to verified fix, where most of the field hands the fix back as a pull request or a recommendation.
