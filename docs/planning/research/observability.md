Vendor research report (official docs only; fetched 2026-10-31). Where I write "not published" the vendor's own docs do not say it. No third-party sources were used.

# 1. Datadog — Bits AI SRE (now "Bits Investigation") + Private Action Runner (PAR)

- Deployment form: Bits itself is SaaS in the Datadog app; no BYOC/on-prem statement. Not offered on app.ddog-gov.com / us2.ddog-gov.com; Bits Remediation and Guardrails are Preview on commercial sites (https://docs.datadoghq.com/bits_ai/bits_ai_sre/take_action/, https://docs.datadoghq.com/bits_ai/). Actions reach the customer environment through a customer-deployed Private Action Runner that "runs in your network, receives action tasks from Datadog" (https://docs.datadoghq.com/actions/private_actions/).
- What is installed: PAR either inside the Datadog Agent (recommended) — a separate process on a Linux/Windows host, a container in the Kubernetes node Agent, or in-process inside the Cluster Agent ("one runner serves the whole cluster"); needs Agent ≥7.81.0, Operator ≥1.28.0 or Helm chart ≥3.231.6, enabled via `clusterAgent.privateActionRunner` in values.yaml (https://docs.datadoghq.com/actions/private_actions/set_up_agent_based/). Or a standalone container (maintenance mode) via Docker or Helm chart `datadog/private-action-runner`, image `gcr.io/datadoghq/private-action-runner:v1.22.1` (https://docs.datadoghq.com/actions/private_actions/set_up_standalone/). Kubernetes RBAC (ServiceAccount/ClusterRole verbs) for the runner: not published on any PAR page; standalone page says only "sufficient permissions to create Kubernetes resources".
- Cloud identity model: Runner identity to Datadog = enrollment keypair; "each runner a private key that Datadog never has access to", Datadog signs every task and the runner verifies the signature (https://docs.datadoghq.com/actions/private_actions/enroll_runner/). Service credentials live in files on the runner at `/etc/dd-action-runner/config/credentials/` (HTTP, GitLab, Jenkins, MongoDB, PostgreSQL, Temporal); no Kubernetes or cloud-IAM credential tab exists (https://docs.datadoghq.com/actions/private_actions/private_action_credentials/). Cloud write actions go through Datadog Connections, each "corresponding to an IAM role with limited scope"; no role names/trust policy published (https://docs.datadoghq.com/actions/connections/). Datadog-side permissions named: `api_keys_read`/`api_keys_write` for API-key enrollment, app key scope `on_prem_runner_write`, `ExecutionGroupWrite` for Execution Policies (in default Admin role), runner access levels Viewer/Contributor/Editor, `Guardrails Read`/`Guardrails Write` for Bits guardrails, "a user role with permission to run actions and resolve the Kubernetes connection" for one-click actions (enroll_runner, set_up_agent_based, execution_policies, take_action URLs above).
- Network path: outbound only — runner "opens an outbound connection to Datadog, polls for action tasks, runs each task against the target service, and returns the result" (https://docs.datadoghq.com/actions/private_actions/). Endpoints listed only as `https://<datadog site>` (Agent runner) and additionally `https://config.<site>` (standalone); custom CA via `SSL_CERT_DIR` (set_up_standalone). No inbound ports stated; no IP allowlist published.
- How actions execute: the runner executes the task against the target (K8s API, service) on Datadog's behalf. Two write-capable escape hatches: (a) predefined scripts — `com.datadoghq.script.runPredefinedScript` runs shell commands declared ahead of time in `script-config.yaml` (`command: ["sudo","systemctl","restart","{{ parameters.service }}"]`), as `dd-agent`/`ddagentuser`; "the runner never runs arbitrary inline commands"; privileged commands require giving dd-agent sudo (https://docs.datadoghq.com/actions/private_actions/run_script/); (b) Remote Action bundle `com.datadoghq.remoteaction.*` including "the rshell bundle (the runCommand action)" and network-path actions, read-only by default (https://docs.datadoghq.com/actions/private_actions/execution_policies/, https://docs.datadoghq.com/actions/private_actions/getting_started/). Allowlist is Agent-side: `private_action_runner.actions_allowlist` in datadog.yaml / `DD_PRIVATE_ACTION_RUNNER_ACTIONS_ALLOWLIST`, e.g. `com.datadoghq.kubernetes.*` (set_up_agent_based). Authorization: ownerless Agent runners use Execution Policies ("single allow or deny rule for a set of actions, together with the Agents it applies to", selected by Agent tags; "Default deny", "Deny overrides allow"; scope e.g. Target Namespaces); owned/standalone runners use Connections; Datadog checks the requesting user before dispatch and never dispatches if not allowed (https://docs.datadoghq.com/actions/private_actions/authorize_private_actions/).
- Approval / autonomy: Bits Remediation offers manual recommendations (copy the `kubectl patch` command), one-click actions (Preview; user clicks Run), and Guardrails (Preview) where admins define which actions, scoped by environment/service/resource tags, with enforcement levels "Ask" (user approval; approvers by team, role or individual) and "Deny" (recommend only). Default enforcement level not published. Separately, "by default, Bits automatically generates code fixes" for code-related root causes (https://docs.datadoghq.com/bits_ai/bits_ai_sre/take_action/).
- Tenant isolation / data handling: Bits docs contain no LLM-provider, training, retention or isolation statements. Only: Execution Policies "do not store credentials"; Datadog never holds the runner private key; generic data_security page (encryption, access controls) says nothing about AI (https://docs.datadoghq.com/data_security/). Bits Code setup page warns prompt-injection safeguards are "imperfect" (https://docs.datadoghq.com/bits_ai/bits_code/setup/).
- Doc URLs used: take_action, bits_ai/, bits_ai_sre/, actions/private_actions/, set_up_agent_based, set_up_standalone, execution_policies, enroll_runner, authorize_private_actions, getting_started, run_script, private_action_credentials, actions/connections, data_security (all under https://docs.datadoghq.com/).
- Not published: runner Kubernetes RBAC (ServiceAccount/ClusterRole rules) and how it authenticates to the K8s API; cloud IAM role names/trust policies; IP allowlist / inbound ports; default guardrail level; which LLM Bits uses, training/retention/tenant-isolation statements; the exact name of the "run actions / resolve connection" permission. (bits_ai/data_security and bits_ai_sre/setup URLs 404.)

# 2. Dynatrace — Davis CoPilot ("Dynatrace Intelligence"), AutomationEngine/Workflows, Site Reliability Guardian

- Deployment form: SaaS. Generative/agentic AI prerequisites list "SaaS" (https://docs.dynatrace.com/docs/platform/davis-ai/copilot/copilot-faq); Workflows/EdgeConnect pages use `<env>.apps.dynatrace.com`. No Managed/on-prem statement for these features.
- What is installed: EdgeConnect, a Dynatrace-published container (`docker.io/dynatrace/edgeconnect`, signed, with SBOM) that "can run in any container runtime", deployed via the Dynatrace Operator (≥1.3.0, `EdgeConnect` CR `dynatrace.com/v1alpha2` with `kubernetesAutomation.enabled: true`) or a plain Deployment (https://docs.dynatrace.com/docs/ingest-from/edgeconnect, https://docs.dynatrace.com/docs/ingest-from/setup-on-k8s/guides/deployment-and-configuration/edgeconnect/kubernetes-automation/edge-connect-kubernetes-automation-operator-supported-setup). "EdgeConnect must run within the Kubernetes cluster where the automation is executed" (https://docs.dynatrace.com/docs/analyze-explore-automate/workflows/actions/kubernetes-automation). RBAC: a ServiceAccount in namespace `dynatrace` plus namespaced Role(s); documented example `apps/deployments` verbs `get,list,patch` with RoleBinding in the target namespace; a ClusterRole example (nodes get/list/watch) with "Use the ClusterRole carefully, and only if it is required"; "We recommend using the Role for all Kubernetes Automation workflow actions" and one EdgeConnect per team (https://docs.dynatrace.com/docs/ingest-from/setup-on-k8s/guides/deployment-and-configuration/edgeconnect/kubernetes-automation, https://docs.dynatrace.com/docs/analyze-explore-automate/workflows/actions/kubernetes-automation/kubernetes-workflows-security-best-practices). ActiveGate/OneAgent are not part of the remediation path in these docs. No Helm chart stated.
- Cloud identity model: EdgeConnect→Dynatrace is an OAuth client with scopes `app-engine:edge-connects:connect/write/read/delete`, `oauth2:clients:manage`, `settings:objects:read/write` (operator setup page). EdgeConnect→K8s API uses the in-cluster ServiceAccount token (`from_file: /var/run/secrets/kubernetes.io/serviceaccount/token`, `restrict_hosts_to: kubernetes.default.svc.cluster.local`) (https://docs.dynatrace.com/docs/ingest-from/setup-on-k8s/guides/deployment-and-configuration/edgeconnect/kubernetes-automation/edge-connect-kubernetes-automation-manual-setup). AWS Connector: OIDC federation (IdP `https://token.dynatrace.com`, `sts:AssumeRoleWithWebIdentity`, audience `<tenant>/app-id/dynatrace.aws.connector`, recommended `sub = dt:connection-id/<id>` condition) or cross-account `sts:AssumeRole` from `arn:aws:iam::314146291599:root` with ExternalId = connection ID; role needs `account:ListRegions`; Dynatrace side `hyperscaler-authentication:aws:authenticate`, `settings:objects:read` (https://docs.dynatrace.com/docs/analyze-explore-automate/workflows/actions/aws/aws-workflows-setup). Dynatrace IAM for workflows: `automation:workflows:read/write/run/admin`, `app-engine:apps:run`, `app-engine:functions:run`; K8s connector `app-settings:objects:read WHERE settings:schemaId = "app:dynatrace.kubernetes.connector:connection"`, `state:app-states:read/write`; workflow actor defaults to creator, service users need `iam:service-users:use` (https://docs.dynatrace.com/docs/analyze-explore-automate/workflows/security, https://docs.dynatrace.com/docs/analyze-explore-automate/workflows/actions/kubernetes-automation/kubernetes-workflows-setup). Agentic AI minimum: `ai:operator:execute`, `mcp-gateway:servers:read/invoke`, `davis-copilot:conversations:execute` (https://docs.dynatrace.com/docs/dynatrace-intelligence/agentic-and-generative-ai/chat-with-dynatrace-assist, https://docs.dynatrace.com/docs/manage/identity-access-management/permission-management/default-policies).
- Network path: outbound only — EdgeConnect "establishes a WebSocket secure connection (WSS/443) to AppEngine and thus doesn't require any inbound connection"; targets `https://sso.dynatrace.com/sso/oauth2/token` and `https://<env>.apps.dynatrace.com` on 443; HTTP proxy with basic auth supported; outgoing requests limited by `restrict_hosts_to` and tenant-side host patterns which "can never exceed the local host restriction" (https://docs.dynatrace.com/docs/ingest-from/edgeconnect). No IP allowlist published. AWS connector calls go direct from SaaS (host pattern `*.amazonaws.com`), not via EdgeConnect.
- How actions execute: Workflows (AutomationEngine, SaaS) send requests to EdgeConnect, which proxies to the K8s API; "the Dynatrace platform can't directly send requests to the Kubernetes API" (kubernetes-automation URL). "All actions correspond to a command of kubectl": apply, delete (with force/grace), get, list, patch, logs (≤6 MB), rollout restart, wait (https://docs.dynatrace.com/docs/analyze-explore-automate/workflows/actions/kubernetes-automation/kubernetes-workflow-actions). No `exec`, no VM/shell command execution, no OneAgent remote execution documented. EdgeConnect limits: 120 s timeout, 6 MB body, 20 concurrent requests.
- Approval / autonomy: Workflows "automatically react to Dynatrace Intelligence events or security problems" (https://docs.dynatrace.com/docs/analyze-explore-automate/workflows) — i.e. fully automatic once authored; no built-in human-approval step is documented. Davis CoPilot/Assist provides "suggested remediation steps" and "is capable of auto-executing generated DQL queries"; per-tool permissions ("you can set permissions for each tool and decide which ones are called"); no autonomous infra remediation stated (https://docs.dynatrace.com/docs/dynatrace-intelligence/agentic-and-generative-ai). Site Reliability Guardian is a quality gate returning `validation_status` pass/warning/fail, run automatically by a workflow or manually (https://docs.dynatrace.com/docs/platform-modules/automations/site-reliability-guardian). Kubernetes Automation RBAC section labelled "Preview release".
- Tenant isolation / data handling: LLMs from "enterprise vendors such as Microsoft Azure AI and AWS Bedrock"; EMEA environments processed in EU region, others in US; vendors "don't store the data you submit"; Dynatrace "may store the prompts ... and the responses" (and intermediate tool-call results for agentic mode), period not stated; "Customer data and customer prompts aren't used for training"; PII masking for generative, PII blocking toggle for agentic ("disabled by default for new environments" from 1.345); "no risk of customer data being shared between environments"; respects user privileges; generative AI enabled by default from 1.335, opt-out in settings (https://docs.dynatrace.com/docs/platform/davis-ai/copilot/copilot-data-privacy, copilot-faq).
- Doc URLs used: listed inline above (all https://docs.dynatrace.com/...).
- Not published: an explicit SaaS-vs-Managed statement for AutomationEngine; a Helm chart; IP allowlist; any human-approval workflow step; Dynatrace prompt-retention period; what `ai:operator:execute` grants; workflow trigger reference (page 404).

# 3. New Relic — Autopilot (formerly SRE Agent) / New Relic AI / Ground Truth MCP

- Deployment form: SaaS (configured at one.newrelic.com; Pro/Enterprise with Advanced Compute or CCU; one agent per org; "not yet available for FedRAMP") (https://docs.newrelic.com/docs/agentic-ai/autopilot/overview/, https://docs.newrelic.com/docs/agentic-ai/autopilot/setup/). No on-prem statement.
- What is installed: nothing beyond standard telemetry agents. Onboarding creates a New Relic-side "system identity to represent the agent" (non-human, scoped to one org), permissions and an alert destination; alerts reach it through a Notification Workflow "AI agent" destination (setup URL). No runner, operator or K8s RBAC.
- Cloud identity model: none to customer cloud/K8s. "The system grants Autopilot standard read-only access to your selected accounts"; user roles `Autopilot: Read, other (Add to Automation)` and `Autopilot (Actions): Read`; setup needs Organization Manager + Authentication Domain Manager (setup URL). Only customer credential is a GitHub fine-grained PAT with `Pull requests: Read`, `Contents: Read`, `Metadata: Read`, "It never writes to GitHub" (https://docs.newrelic.com/docs/agentic-ai/autopilot/connect-to-github/).
- Network path: no action component in customer environment; GitHub lookups go to `https://api.githubcopilot.com/mcp/` (connect-to-github URL). Partner path (marketing blog): EventBridge→Lambda posts alert payload to AWS DevOps Agent webhook (https://newrelic.com/blog/ai/aws-devops-agent-and-new-relic).
- How actions execute: it doesn't. "Autopilot recommends actions but does not take them. A person reviews and acts." (overview URL); "No action execution: Autopilot investigates and recommends but doesn't run remediation actions, such as rollbacks or restarts" (https://docs.newrelic.com/docs/agentic-ai/autopilot/connect-to-slack/); "does not write back to external systems such as Confluence or ServiceNow". Marketing page claims "Execute approved runbook actions with human confirmation" (https://newrelic.com/platform/sre-agent) — not backed by any docs page. Azure SRE Agent / AWS DevOps Agent integrations consume New Relic's MCP server; any execution happens in the partner agent (https://newrelic.com/blog/news/microsoft-ignite-2025-agentic-ai-integrations, marketing). No VM-level execution.
- Approval / autonomy: "human-in-the-loop ... for certain decision making" with "configurable controls for Autopilot access and permissions" (https://docs.newrelic.com/docs/agentic-ai/autopilot/use-autopilot/); 100 requests/hour/org; admins can reduce account grants below read-only (overview, setup URLs). No levels enumerated.
- Tenant isolation / data handling: subject to "Generative AI Service Specific Terms"; analysis "visible to any users with Autopilot interaction access, regardless of their direct access to those accounts" (setup URL); Slack credentials "pass through request headers only"; GitHub token in "the Secrets Service"; retention of agent MELT data "may differ from your general account retention settings" (overview). LLM provider not stated. New Relic AI "uses ... your telemetry data" to improve responses (https://docs.newrelic.com/docs/new-relic-solutions/new-relic-one/core-concepts/new-relic-ai/). Docs conflict: Autopilot "may be used with HIPAA accounts" vs NRAI "not currently available for HIPAA or FedRAMP".
- Doc URLs used: autopilot/overview, /setup, /use-autopilot, /connect-to-github, /connect-to-slack, agentic-ai/mcp/overview, core-concepts/new-relic-ai (docs.newrelic.com); platform/sre-agent, press-release/20260623-2, two blogs (newrelic.com, marketing).
- Not published: LLM provider, training policy, data residency, retention period; what the marketing "runbook actions" mechanism is; autonomy levels/approvers; any integration docs page (agentic-ai/integrations 404).

# 4. Grafana Labs — Grafana Assistant Investigations and Sift

- Deployment form: Grafana Cloud; Assistant can run in self-managed Grafana only when "connected to a Grafana Cloud Assistant backend", and there "investigations, infrastructure memory, and MCP configuration are hidden" (https://grafana.com/docs/grafana-cloud/platform/grafana-assistant/, https://grafana.com/docs/grafana-cloud/platform/grafana-assistant/privacy-and-security/security/). Investigations need a separate entitlement. Sift is "a free diagnostic assistant included in Grafana Cloud" (https://grafana.com/docs/grafana-cloud/alerting-and-irm/machine-learning/sift/).
- What is installed: nothing specific — investigations/Sift query the stack's Prometheus/Loki/Tempo data sources (https://grafana.com/docs/grafana-cloud/ai-tools/machine-learning/sift/sift). Telemetry comes from the Kubernetes Monitoring Helm chart (Alloy, kube-state-metrics, Node Exporter) (https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/configuration/config-k8s-helmchart/); its RBAC is not stated on that page. No runner/operator for actions.
- Cloud identity model: manual investigations "use your identity and data source permissions"; automated ones from alerting/IRM webhooks "use service credentials and that service identity's permissions" (https://grafana.com/docs/grafana-cloud/platform/grafana-assistant/platform/investigation/); automations run on "the existing Assistant tenant service account and the organization's system-initiated token pool" (https://grafana.com/docs/grafana-cloud/platform/grafana-assistant/privacy-and-security/rbac). Grafana RBAC: `grafana-assistant-app.investigations:create` (Assistant Investigation User role; Editor includes it), `grafana-assistant-app.settings.investigations:read/write`; Sift start: Viewer by default (sift page) vs Editor/Admin (ai-tools sift page) — docs conflict. No cloud IAM credentials.
- Network path: requests "route through Grafana Cloud and never go directly from your browser to third parties"; self-managed plugin forwards to the paired Cloud backend; web search via Amazon Bedrock AgentCore or Claude web search (https://grafana.com/docs/grafana-cloud/platform/grafana-assistant/privacy-and-security/privacy/). Alert-enrichment "External enricher" calls a customer URL with the alert payload (https://grafana.com/docs/grafana-cloud/observe-and-act/alert-and-measure-reliability/alerting/configure-notifications/alert-enrichment/). No inbound connection to customer infra.
- How actions execute: no remediation in customer infrastructure — investigations produce "Findings and recommended next steps" / "actionable recommendations for mitigation and remediation" (investigation URL, https://grafana.com/blog/grafana-assistant-ga-assistant-investigations-preview/). Writes are inside Grafana only: "Assistant actions run under your user identity", audit-logged (security URL); Cloud MCP "Write" level "lets a connection create, modify, and delete anything the user can in Grafana" (rbac URL); OSS MCP server mutating tools: `update_dashboard`, `create_datasource`, `alerting_rules_write`, `alerting_silences_write`, `update_alert_group`, `create_incident`, annotations, snapshots (https://grafana.com/docs/grafana/latest/ai-tools/mcp/reference/mcp-tools-table/). Coding agents have Managed Sandboxes and "automatic PRs" (rbac URL). No VM/shell execution.
- Approval / autonomy: investigations start automatically from alerts/IRM webhooks (default 50 starts per 20 min; "No organization-wide setting disables investigation automations"); humans steer with Stop/Disprove/Reopen; scheduled checks stop after 24 h or 100 checks; no approval gate (nothing to approve) (investigation URL). Alert enrichment warns not to run on the all-alerts scope.
- Tenant isolation / data handling: LLMs "Anthropic, Google Vertex AI, or Amazon Bedrock using Claude models", not selectable; "zero retention" at providers; conversations stored in-tenant in the stack's region; chat retention 30/90/180 days (planned default 90 from 2026-09-01); "We never use your organization's data to train AI models"; EU stacks in-region, US "Partial", others may run outside region; "Grafana Cloud isolates data by tenant and personal conversations by user"; Assistant can only access what the user can; SOC 2 Type II, ISO 27001 (privacy and security URLs).
- Doc URLs used: listed inline above.
- Not published: Kubernetes RBAC of the monitoring Helm chart (on the pages read); the exact permissions of the automated-investigation service identity; any remediation path into customer infra (none exists in docs); the MCP incident/Sift guide page (404).

# Cross-vendor summary
Only Datadog (via PAR, Execution Policies, Guardrails Ask/Deny) and Dynatrace (via EdgeConnect + Workflows, kubectl-equivalent actions, fully automatic once authored) execute in customer infrastructure; both are outbound-only components deployed by the customer. New Relic Autopilot and Grafana Assistant/Sift are recommend-only; their writes stay inside their own SaaS. None of the four publishes an IP allowlist for the action component, and only Dynatrace publishes concrete Role/ClusterRole examples and an IAM trust policy.
